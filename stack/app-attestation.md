# App Attest authenticated backend sessions

Use this playbook when an iOS app needs to prove that requests came from an authentic app installation and then bind a paid RevenueCat identity to that installation.

This is an installation-authentication layer. It does not move local transactions to a backend and it does not make RevenueCat's `appUserID` a credential.

For an explicitly accepted accountless alternative that supports promotional Pro without an Apple receipt, see [Windfall's accountless decisions](app-attestation-accountless-learnings.md). Choose the identity-assurance model before copying this playbook: the purchase-proof model below and first-attested-claim entitlement mapping are different policies, particularly for private customer data.

## Responsibilities

Keep the implementation split by ownership:

| Layer | Owns |
| --- | --- |
| SwapFoundationKit | App Attest key generation, Keychain persistence, challenge hashing, attestation, and assertions |
| SwapProKit | Extracting an active RevenueCat entitlement and a verified StoreKit transaction JWS |
| Host app | Session bootstrap, app-specific API client, purchase-binding timing, entitlement policy, and UI behavior |
| Host Worker | Attestation/assertion verification, assertion counters, session tokens, RevenueCat correlation, rate limits, and persistence |

The host app should use the SFK and SwapProKit APIs after those package versions are available. A temporary app-local adapter is acceptable only when the host still resolves older package revisions; document it and remove it after the package update lands.

## Security model

1. The server creates a short-lived, one-time challenge for enrollment or session refresh.
2. The app hashes the opaque challenge once with SHA-256 and sends the App Attest attestation/assertion generated by Apple.
3. The server verifies the App Attest certificate chain, app ID, nonce, key ID, environment, and assertion counter.
4. The server issues a short-lived bearer session tied to the App Attest key.
5. The app sends that bearer on backend requests. `X-App-User-ID` may remain as context/compatibility data, but it must not authorize access by itself.
6. A paid installation submits a verified StoreKit transaction JWS. The server checks the transaction/product claims and correlates the transaction with the RevenueCat customer record before binding the App Attest key to the RevenueCat `appUserID`.

App Attest validation should follow Apple's server-side guidance: <https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server>.

## Host app implementation

### 1. Add the package capabilities

Update the host's SwapFoundationKit and SwapProKit dependencies to revisions containing:

- `AppAttestService` / `AppAttestProviding`
- `RevenueCatPurchaseProofProvider` / `SwapProPurchaseProof`

Keep app-specific policy in a host `BackendSessionService` actor. The service should:

- load a previously issued session from secure Keychain storage;
- load or generate one App Attest key and persist its key ID with `ThisDeviceOnly` accessibility;
- enroll the key once per installation;
- refresh a session before expiry using a new assertion;
- clear the bearer from memory when bootstrap fails;
- bind a purchase only after RevenueCat reports the entitlement active and StoreKit returns a `.verified` transaction;
- refresh the session after purchase binding so the bound RevenueCat identity is reflected in the next server session.

Do not put App Attest or RevenueCat network logic in `AppDelegate`. Start the actor from the app lifecycle after the core managers are initialized.

### 2. Configure entitlements

Production target:

```xml
<key>com.apple.developer.devicecheck.appattest-environment</key>
<string>production</string>
```

Development target:

```xml
<key>com.apple.developer.devicecheck.appattest-environment</key>
<string>development</string>
```

Use separate bundle IDs and Keychain keys for development and production. Never accept development attestation on the production Worker.

### 3. Attach the session to every backend request

The shared request header provider should always send:

```text
X-App-User-ID: <RevenueCat appUserID>
Authorization: Bearer <session token>
```

The bearer is the credential. The RevenueCat ID is a server-checked identity hint and must be compared against the bound session identity. Client-side Pro state must not decide whether the header is sent.

### 4. Use the purchase proof only for binding

The purchase proof should contain the RevenueCat app user ID, product ID, transaction ID, original transaction ID, and StoreKit verification JWS. Do not send an arbitrary RevenueCat ID and do not bind before the server has verified the transaction correlation.

## Worker implementation

The Worker needs four endpoints:

| Endpoint | Purpose |
| --- | --- |
| `POST /v1/auth/challenge?purpose=enroll` | Issue a one-time enrollment challenge |
| `POST /v1/auth/enroll` | Verify and store the App Attest public key |
| `POST /v1/auth/challenge?purpose=session` | Issue a one-time session challenge |
| `POST /v1/auth/session` | Verify an assertion and issue a short-lived bearer |
| `POST /v1/auth/bind-purchase` | Correlate a verified purchase and bind the key to RevenueCat |

Persist at least:

- hashed, one-time challenges with purpose, expiry, and consumed state;
- App Attest key ID, public key, environment, optional bound RevenueCat ID, and last assertion counter;
- hashed session ID, App Attest key reference, and expiry.

Use a cryptographically random session identifier and sign a short-lived token with `AUTH_SESSION_SECRET`. Store only the hash of the session identifier in D1. Reject replayed challenges, expired tokens, wrong app IDs, wrong environments, key rebinds, and non-monotonic assertion counters.

For Cloudflare Workers, configure Node compatibility and use a maintained App Attest verifier that validates Apple's attestation/assertion structures. Keep the verifier behind a small shared module so it can be replaced or upgraded without changing route policy.

## Configuration

Required Worker variables:

```text
AUTH_ENFORCE_SESSIONS=false   # rollout default
AUTH_SESSION_SECRET=(stored as a Worker secret)
APP_ATTEST_BUNDLE_ID=<production bundle ID>
APP_ATTEST_TEAM_ID=<Apple development team ID>
APP_ATTEST_ALLOW_DEVELOPMENT=false
```

Create the secret locally and store it only in the Worker secret store:

```bash
openssl rand -base64 32
npx wrangler secret put AUTH_SESSION_SECRET
```

Apply the D1 migration before deploying the Worker. Keep enforcement disabled while the new app version is rolling out. The new routes can be deployed safely in compatibility mode because existing requests continue through the legacy path.

## Release sequence

1. Merge and publish the updated SwapFoundationKit and SwapProKit revisions.
2. Update the host app's package revisions and ship the App Attest-enabled app.
3. Apply the D1 migration to the production database.
4. Deploy the Worker with `AUTH_ENFORCE_SESSIONS=false`.
5. Test the release on a real production-entitled device: launch, API request, purchase/restore, session refresh, and logout/reinstall behavior.
6. Monitor Worker errors and adoption of the new app version.
7. Set `AUTH_ENFORCE_SESSIONS=true` only when the remaining old-client population is acceptable or an update gate is in place.
8. Deploy the Worker again and verify authenticated requests, free-tier requests, Pro requests, and failed/replayed proofs.

If enforcement causes trouble, set it back to `false` and redeploy. The migration is additive; do not delete the auth tables during rollback.

## Request volume

Do not generate an App Attest assertion for every API request. Enrollment happens once per installation, and assertions are used for session issuance/refresh and purchase binding. Ordinary requests reuse the short-lived bearer token.

## Verification checklist

- [ ] SFK App Attest APIs are used for key storage, hashing, attestation, and assertions.
- [ ] SwapProKit supplies only verified StoreKit purchase proofs; the host owns policy.
- [ ] Production and development entitlements use the correct bundle IDs/environments.
- [ ] Every personal-backend request sends the bearer and the RevenueCat ID context header.
- [ ] The server never authorizes from `X-App-User-ID` alone.
- [ ] App Attest certificate, app ID, nonce, environment, and counter checks are server-side.
- [ ] RevenueCat binding cross-checks transaction ID and product ID against the customer record.
- [ ] D1 migration is applied before enforcement is enabled.
- [ ] `AUTH_SESSION_SECRET` is configured as a secret, never a committed variable.
- [ ] Worker typecheck/tests and a Release-like iOS build pass.
- [ ] A real-device production smoke test passes before enabling enforcement.
